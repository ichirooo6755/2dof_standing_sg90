# XIAO nRF54LM20Aの起き上がり確認

対象はSG90 2個、PowerBoost 500、XIAO nRF54LM20A Sense。旧nRF54L15 Senseと新基板は同じ向き・表裏で取り付けたと使用者が確認した。下段D0・上段D1の中央は、それぞれ1500 µs・1464 µsでアームがまっすぐと目視確認済み。

新基板もLSM6DS3TR-Cを使用するが、IMUはnPM1300 LDO1から給電し、I2CはWire1、CSをHIGHにする必要がある。Seeedの公開KiCad設計ではIMUの搭載角が旧基板と180°異なり、同じUSB方向なら変換は`−X,−Y,+Z`となる。奥側への傾斜に対するセンサー応答は実機で確認した。左右方向の符号は設計に基づく設定で、交換後の独立した実機確認は未了。

## 制御側の修正

- LM20AのD0/D1の実GPIO番号を使ってパッド読み取りを有効化し、旧基板の番号を流用しない。
- 倒れてからの静止待ち中は目標角を保持し、連続300 msの条件を満たした後に方策を実行する。待機中に方策を実行していた版は、この指定を満たしていなかった。
- LM20Aは128 MHzでビルドする。倒れた状態でサーボ出力を停止した比較では、方策の最大計算時間が64 MHzで13,391 µs、128 MHzで6,763 µsだった。これは同一環境の各観測期間中の最大値で、最悪時間の保証ではない。
- 128 MHzの計算のみの試験では、静止待ち中の記録15フレームで目標と行動は0のまま、その後の回復段階では目標角が下段90°・上段約87°まで達した。SG90には角度の読み戻しがないため、これらは物理的な回転角ではない。方策の重みや角度に対するパルス倍率は変更していない。
- 起動時にセンサー準備が15秒を超えてもPWMを停止したまま待ち続け、初期化失敗は2秒間隔で再試行する。準備後は従来どおり中央を1秒保持してから自動監視に入る。運転中の異常停止や手動停止は解除しない。

## 実機で分かっていること

2026-11-13、128 MHz版を実機へ書き込み、平らな状態で25秒間、mode 4、中央指令、IMU受信エラー0、停止なしを記録した。奥側へ倒した試験では、使用者は「少しだけ動いて止まった」と報告。最後に受信したのは静止待ち約289 ms・中央指令のフレームで、その直後にUSBが切れ、基板が再起動した。回復指令の最初のフレームが物理的に出たかは分からない。再接続後に停止指令を送り、出力OFFを確認した。

その後、使用者はUSBを差し直した後に手を離して起き上がれたと報告した。復帰中のログは取得できておらず、その後の12秒間の直立記録は自動監視継続、IMU受信エラー1回だった。別の接続切断も発生しており、再現性や原因は未確定。

サーボ端子D0/D1をLOWに保ち、代わりに基板上のLED端子でパルスを生成する一時診断版でも試験した。記録した倒れ姿勢を入力し、同じ方策計算とパルス生成を30.1秒間動かして、USB切断とIMU通信エラーは発生しなかった。パルス指令は下段524〜2500 µs、上段500〜2461 µsで、方策の最大計算時間は6701 µsだった。これは実サーボへの出力や負荷時の試験ではなく、計算とパルス生成の処理だけでは停止を再現しなかったことを示す。

その後、自動起き上がり版を書き戻し、台座を平らに置いた状態で中央指令1500/1464 µs・mode 4を受信したが、約0.5秒の記録後にUSB通信が切れ、ポートが消えた。この記録だけでは基板の再起動や切断原因は特定できない。切断までのIMUエラーカウンターは21だったが、いつ発生したかはこの短い記録では分からない。

使用者が電源を外してからサーボ2個の3線コネクタを外し、USBだけを接続した後、平らな姿勢を続けて25秒と50秒記録した。D0/D1に中央パルスを出しながら自動監視を継続し、USB切断は発生しなかった。この約75秒間にIMU受信失敗は累計2回あった。これは直立時の比較であり、サーボの負荷が切断の原因だと確定するものではない。

サーボを外したまま倒した次の記録でも、静止待ち297 ms・中央指令を最後にUSBが切れた。使用者はその際、USBケーブルには触れておらず引っ張られていなかったと報告した。サーボ負荷だけで切断を説明することはできない。最初の回復指令が出たか、またこの切断時に本体が再起動したかは記録できていない。

その後、サーボ2個を外し、機体を動かさず、左右に倒れたときの姿勢と角速度をプログラムへ入力して再現試験した。両出力をD0/D1にした場合と、D1だけを実端子に出してもう一軸をLEDに振り替えた場合は、それぞれ静止待ち298 ms・299 msの記録直後にUSBが切れた。前者は再接続後に起動直後の状態を確認した。同じ入力で両軸ともLED端子に出すと20秒、D0だけを実端子に出すと12秒、回復計算とパルス生成が続いた。ただしD0だけの再試験でも一度USBが切れ、その次は12秒継続したため、D1だけの故障と断定できない。D1の信号線はXIAO側では取り外せないとはんだ接続を使用者が報告した。

さらに同条件で各3秒・6回ずつ比較すると、LED端子への出力では6回とも復帰計算が継続したが、両軸をD0/D1へ出すと6回とも通信が切れた。テレメトリーを10 Hzに減らした版と、ニューラルネットワークの計算を近似して高速化した版も、それぞれ6回とも切断した。固定動作、端子の読み取りを外した版、レジスタへ直接書く版、タイマーPWM版も解消を確認できなかった。いずれもサーボを外した一時診断であり、回路または制御のどちらが原因かを確定するものではない。これらの未検証の代替処理は自動運転版に採用していない。

D1の入力バッファも無効にした版で切断は残った。自動起き上がり版へ戻した後、平らな状態でも最初の状態応答を受信してから約1.7秒でUSB通信が切れた。続いてサーボとLiPoを外したまま `servo_center` のみを書き込み、D1の小往復を開始した試験でも、センサー・学習計算なしでUSBが切れた。基板側の信号線は接続されたままで、USBケーブル・コネクタ・電源・基板・配線のいずれかに起因する可能性も残る。

その後の上段単独確認では、下段D0をLOWに保って上段D1のみへパルスを送り、使用者は上段がごく小さく動いたと報告した。中央指令1464 µsを送った後にUSBが切れ、往復は完了しなかった。LiPoはPowerBoostに接続中との回答だった。再起動調査用の一時ファームでは、中央保持指令の直前にMCU稼働時間29,407 msを記録し、切断後の再接続時は970 msだったため、USB通信に加えてMCUも再起動したことが分かった。再起動理由の値は0で、電圧低下・配線・USB・基板のどれかを確定できていない。サーボ軸の実角度は取得できないため、上段サーボ単体の良否も未確定。

後の接続では、旧版が `automatic startup: IMU initialization timeout` として停止している一方、センサーと姿勢推定は準備済みになっていた。旧版は起動準備を15秒で打ち切り、その後センサーが準備できても待機から自動復帰できなかった。起動待ちの修正はこの停止条件を対象とし、上記のUSB切断の原因が同じだとはまだ確認できていない。

修正版の一時診断版では、起動から17秒間センサー未準備を模擬した。D0/D1はLOWに保ち、LED端子へパルスを振り替えた状態で、準備後に中央保持を経てmode 4へ移行し、実IMUの倒れ姿勢で方策も実行した。25秒の記録中にUSB切断とIMU受信失敗はなかった。これは起動待ちからの自動再開と計算の確認であり、サーボ付きでの成功を示すものではない。

使用者がサーボ2個を再接続して台座を平らに置いた後、`sg90-lm20a-3` を書き込み直した。20秒間の直立記録はmode 4、中央指令1500/1464 µs、USB切断なし、IMU受信失敗0回だった。サーボ電源のLiPoも接続されていた。使用者は奥側から起き上がったが左右では動きが小さいと報告。左右姿勢の記録は静止待ち285 msを最後にUSBが切れ、回復指令は記録できていない。

停止中のテスター値はXIAO 3V3–GNDが3.3 V、PowerBoost 5V–GNDが5.2 V。これはサーボが動き始める瞬間の電圧降下を測定したものではない。実際のサーボ出力、給電、USB接続、基板や制御タイミングのどれが切断に関係するかは未確定。

## ビルドと確認

`./tools/build_standing_lm20a.sh` は128 MHz版をビルドする。`--upload SERIAL_PORT` を付けたときだけ書き込む。`python3 firmware/standing_xiao/tests/test_board_port.py` は両ボードのGPIO対応、サーボパルス、IMU軸変換、静止待ちとその再計時をホスト上で確認する。これらのテストや停止中の波形記録は、負荷をかけた実機が安定して起き上がることを保証しない。
